# Private working draft: a green test process can still lack passing evidence

Status: Stage A candidate notes, not published. Human set the real Qwen validation goal and physical GPU0 constraint. The Builder agent implemented the changes and ran the local probes; an independent Regulator must still review the candidate. No personal independent-implementation or performance claim is implied.

The earlier entry accepted unittest.wasSuccessful(). During this resumption, the Regulator pointed out that a real @expectedFailure test can fail its body while the native runner still exits0. The Builder copied the required measurement suite to an isolated temporary directory, retained all mandatory IDs, and made one body fail under @expectedFailure. The native runner exited0 and the original required wrapper also exited0. The new red test records that behavior in required-expectedfailure-red.log.

The Builder added expectedFailures and unexpectedSuccesses to the wrapper's machine result and required both counts to be0. The same behavioral test then passed. A later probe found a related gap in pytest: @pytest.mark.xfail(strict=False) with a passing body became a normal passing JUnit testcase, so JUnit's skipped/failure counts alone were insufficient. required-pytest-xpass-red.log preserves that second false green. A plugin loaded only by the required entry now records actual wasxfail reports and returns failure for either xfail or XPASS. Ordinary passing tests still pass; the green receipt preserves the result.

The design choice keeps upstream native behavior intact and puts the stronger evidence contract at the required entry. Merely checking a process's exit0 would be adequate for a developer's optional test run; this gate promises that required tests actually completed with passing assertions. The added report and counter checks serve that narrower promise. They do not prove the tests cover every defect. Isolated native Node skip/todo, empty unittest discovery, unexpectedSuccess and sealed-input corruption probes exercise the same public commands rather than editing summary JSON.

The GPU question has a different failure mode. Human said CUDA_VISIBLE_DEVICES=0 and meant the server's first RTX4090. The historical run targeted physical GPU3 and presented it inside the container as logical0. Changing a run label to GPU=True or replacing the UUID string cannot establish which device executed a request. The new code requires raw host/container nvidia-smi receipts, full model inspect, source/config identities and their shared UUID before it analyzes a real-labeled run. A separate externally pinned manifest protects the receipts after handoff. These checks still need a fresh authorized real GPU0 execution and independent review. SSH currently closes before authentication, so the Builder has not produced that new real sample.
