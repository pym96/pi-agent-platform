# 私稿：清理成功为什么不能代表压测完成

状态：内部博客与X草稿，未发布。来源Pi13 SC06、source45faa的formal01原件与source260831的CPU修复；完整新formal02独立复核仍不能代替最终候选验收。

我们要在共享4090上测平台与模型直连，约束是固定请求库存、硬截止、只清理自己资源。最初把原生启动器返回0和清理结果当作闭环的直观信号。正式第一轮中，监控发现额外GPU进程并清理自有服务；后续健康检查连接拒绝。额外进程归属并未查明，不能归因于谁的作业。

真正的问题在记录层：一个点已经产生20条请求记录、10个成功和10个失败，随后的idle检查异常却用新错误对象替换了已有summary。图表遗漏这个点，外层仍返回0。完整库存其实是240计划、60已发、180未发，不是完整矩阵。清理状态回答“资源是否收回”，工作负载状态回答“计划是否执行完”，二者不能合并。

修复保留已测metrics并附加stop_reason，写明complete或stopped，停止向client和native传播非零结果。独立R用真实HTTP监听端口在点结束前关闭的反例验证：旧版丢指标/exit0，新版保留20/20首点、后220未发并exit2。后来R又发现候选外协调器只记录native失败而自身仍0，因此固定入口也检查本批新鲜native/watch结果，unknown同样向外失败。没有改业务限流或延长截止来凑完成。

另一个执行判断失误是等R释放服务器后才组装完整启动命令，错过旧phase4所需启动余量。Builder保留未用GO并拒绝启动；Master另批固定窗口后，先冻结完整入口再签GO。新一轮完整240请求中219成功、19直连queue_deadline、2平台upstream503。失败分母不消失，成功P95才有解释条件。

这件事的可复用部分是把工作进度、观测错误和资源回收分开建模，并让失败状态穿过每层进程边界。它不证明推理更快。Human提出学习方向和负载要求，Master制定预算与授权，Builder Agent实现和执行，Regulator Agent独立构造反例与复核；不写成人本人独立完成。

原件定位：[完整结果与限制](README.md)、[中断修复](../20261110-interrupt-repair/README.md)、external-artifacts.json中的formal01不可变归档。本文仅在授权Evidence内留痕，未晋升简历事实。

## X thread 草稿（未发布，无公开博客链接）

1/ 共享GPU压测最容易误读的信号：清理成功、进程exit0，并不代表计划全部执行完。我们的第一轮计划240次，实际只发60次；后续健康检查异常还覆盖了一个已经生成的点摘要。

2/ 修复的重点是保留已有指标与未发库存，把workload complete/stopped和cleanup分别记录，并把失败穿过client、launcher和最外层进程。独立HTTP反例能稳定复现旧版丢数据/exit0，新版保留分母/exit2。

3/ 后续完整一轮是240发出、219成功、21失败或拒绝。成功P95旁必须有成功n/计划20：直连C4成功8/20，不能因为剩下8次较快就说系统更快。单轮小样本也不代表C10K或硬件极限。由Agent实施与独立复核，尚无对外事实披露授权。
