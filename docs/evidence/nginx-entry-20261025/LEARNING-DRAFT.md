# 私有博客草稿：加了 Nginx，原来的 400 为什么变成 413？

状态：Builder过程记录与博客/X草稿，未公开、待独立复核，不作为简历事实。文中的实施与排查由Builder Agent完成。

Human问“Nginx用来分流吗”，随后授权把入口接到现有Pi平台。这一轮要学习的是：在Go前面加一层代理，原来的任务、错误和流式协议是否还成立。Master保留现有单Go控制器，另用两个无状态fixture演示轮询。

我最初给Nginx设了32KiB请求体上限。Go本来只读取最多16384字节，prompt还限制8192字节。我当时认为代理上限比应用宽松，正常请求不会受到影响。前几轮测试也只覆盖了应用限制附近的输入。

准备交接时，我重新看了更大的非法输入。超过32KiB以后，Nginx会在请求到达Go前拒绝；原来Go返回的400，可能变成代理的413。这里的问题来自两层各自执行请求体规则，正常请求通过不能证明拒绝语义一致。

我先补了一个40,000字节prompt的对照测试。run-07源码`1a97f28`的实际结果是：直连400，代理413；必需平台测试失败。原件保留了客户端收件和Nginx日志，完整入口随后停栈，没有继续跑新的性能矩阵。这次红测把源码推断变成了可复查的行为差异。

Master确认本轮要求保留Go的请求体拒绝语义。我在获准配置范围内把`client_max_body_size`设为0，关闭`proxy_request_buffering`，让Go继续执行原来的读取上限；我没有扩大Go允许的输入，也没有修改它的错误码。测试同时比较两条路径的状态和错误体，避免只看一个400就宣称一致。

新源码`9a00285935dd61c29c9a2ddf9ebcfc49ad29d3ba`在run-08重新执行完整CPU、实际Pi SDK平台、原12点HTTP矩阵和lab自检，均通过。最终候选仍需独立Regulator与同SHA CI。这里证明的是私有CPU切片的协议行为，不能推出公网防护能力或Qwen吞吐。

如果以后把Nginx作为公开入口，独立入口限制可能有工程价值；那时需要把代理拒绝状态、大小上限和应用契约一起定义。本轮先完成透明代理的已定范围，不把临时加上的限制当成默认产品需求。

来源：Pi #15 / NG1.1、run-07的platform-tests.stderr与client.jsonl、run-08相应原件及REPORT。Human负责方向和问题，Master负责合同与取舍，Builder Agent负责实现和排查；尚未授权发布。

## 配套 X 草稿

给Go服务加Nginx时，我把代理请求体上限设成32KiB，应用只读16KiB，先以为不会影响原行为。新增40,000字节输入后，直连400、代理413：代理在Go之前拒绝了请求。

本轮要求保留应用协议，于是把读取上限继续交给Go，关闭代理请求缓冲，补状态和错误体对照。旧红测保留，修复后重新跑完整CPU切片。实验只涉及私有synthetic服务，候选待独立复核，未证明模型容量提升。
